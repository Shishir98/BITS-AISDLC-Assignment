# Smart Todo & Task Management API Constitution

## Core Principles

### I. Specification-First Development
All implementation MUST follow approved Spec Kit artifacts. Requirements and
acceptance criteria MUST NOT be weakened, removed, or reinterpreted merely to make
tests pass. When a requirement needs to change, update and approve its governing
specification before changing implementation or tests.

### II. Clean Architecture
Keep API routes, business logic, data models, and persistence clearly separated.
Dependencies MUST follow those boundaries; persistence details MUST NOT leak into
route or business rules. Prefer the simplest modular design that satisfies approved
requirements; avoid unnecessary complexity.

### III. Deterministic Behaviour
Identical inputs and application state MUST produce predictable results. Business
logic MUST NOT depend on external AI services, unpredictable network calls, or
uncontrolled environmental state.

### IV. API Contract Integrity
Endpoints MUST define explicit request and response schemas, validate inputs, use
appropriate HTTP status codes, and return consistent error responses. API errors
MUST NOT expose internal stack traces or implementation details.

### V. Data Integrity
Persist application data as JSON and isolate persistence behind testable interfaces.
Writes MUST serialize to a temporary file in the same directory and atomically
replace the stored file only after the new data is complete. Malformed JSON MUST
raise a testable `MalformedStoredDataError` with the stable identifier
`malformed_stored_data`; it MUST NOT silently reset, replace, or overwrite the
stored data. Tests MUST verify the error and preservation of the original file.

### VI. Security
Never commit secrets, credentials, or local environment files. Validate untrusted
input, avoid unsafe execution, and keep sensitive or internal implementation
details out of API responses. Security-relevant changes MUST be assessed and
validated before acceptance.

### VII. Requirement-Driven Testing
Every approved acceptance criterion MUST map to at least one automated test, and
all mandatory automated tests MUST pass. Tests MUST cover positive, negative,
boundary, and invalid-input scenarios where applicable. Automated application
tests MUST NOT rely on external network services. A failing test MUST be repaired
by correcting implementation or approved specifications, never by deleting or
weakening required coverage.

### VIII. Code Quality
Python code MUST use type annotations, meaningful names, and modular structure.
Ruff MUST report zero lint violations. Bandit MUST execute for static security
analysis, and its findings MUST be reviewed and resolved or explicitly documented
before human acceptance.

### IX. Independent Validation Harness
Harness scripts and mandatory checks MUST remain separate from application source
and operate independently of the generated implementation. Changes to mandatory
tests, expected results, or validation controls require explicit, recorded human
approval before they take effect. Mandatory harness failures MUST produce a
non-zero exit code. Results MUST be generated by the runner, not manually edited.
The coding agent MUST NOT be able to disable mandatory checks, delete or weaken
failing tests, or alter recorded results. Harness integrity and results MUST be
retained for review.

### X. Traceability and Evidence
Preserve the initial and final implementations, test and security-analysis results,
failure evidence, and repair history. Keep evidence attributable to the version
validated so that changes and validation outcomes can be independently reviewed.

### XI. Human Accountability
Automated PASS results MUST NOT constitute automatic acceptance. A human MUST
review the final implementation and evidence, then record an explicit ACCEPT or
REJECT decision.

## Engineering Constraints

The project targets Python 3.12 with FastAPI and Pydantic, and uses JSON-based
local persistence. New dependencies, external services, or persistence technologies
MUST NOT be introduced without approval in the relevant Spec Kit artifacts.
Implementation MUST preserve the architecture, deterministic behavior, API
contracts, and data integrity defined by these principles.

## Lifecycle, Validation and Evidence

Specifications and acceptance criteria MUST be approved before implementation.
Validation MUST run the independent harness against the final implementation.
Release evidence MUST show: zero Ruff lint violations; passing results for all
mandatory automated tests; at least one automated test for every approved
acceptance criterion; and Bandit execution with findings reviewed and resolved or
documented. Automated application tests MUST NOT depend on external network
services. Mandatory harness failures MUST return a non-zero exit code, and
validation results MUST come directly from the runner. Record failures as well as
passes, and retain evidence of each repair and subsequent validation. A change is
ready for human review only when required checks have completed and their results
are available; acceptance remains the human decision defined above.

## Governance

This constitution governs the full development lifecycle and takes precedence over
conflicting project practices. Amendments MUST be proposed with their rationale
and impact, reviewed and approved by a human, and reflected in the constitution
before dependent work proceeds. Version changes follow semantic versioning:
MAJOR for incompatible governance changes, MINOR for new or materially expanded
principles or sections, and PATCH for non-semantic clarifications. Update the
amendment date with each change.

Compliance MUST be reviewed when specifications are approved, implementation is
planned, and final validation is assessed. Any conflict with this constitution
MUST be resolved through an approved amendment or by bringing the work into
compliance; automated validation does not replace human review or the explicit
final decision.
